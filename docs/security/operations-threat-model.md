# Threat model — operations: operators, export, deletion, dead letters, rotation, alerts

**Status:** Proposed in Phase 6 T1, before the surfaces exist. Decisions [0014](../decisions/0014-failure-handling-and-alerting.md) (failures, dead-letter queue, operators, alerts) and [0015](../decisions/0015-data-lifecycle.md) (retention, export, deletion) define them, and the [Phase 6 plan](../plans/phase-6.md) § Secret rotation defines rotation. T1 built the database side: migration 0009's triggers and CHECKs, and the `OPERATOR_GITHUB_IDS` parser. T3, T4 and T5 implement the rest, each with the scenarios named here. T6 reviews the built surfaces adversarially, then fixes each finding or records it below.

Phase 6 adds the first surfaces that cross workspaces on purpose (operators), move a workspace's data out of ShareRepo (export), or destroy it (pruning, purge, account deletion). Each one can turn a small bug into a cross-tenant leak or an unrecoverable loss.

## Assets

- **Tenant isolation.** A workspace's repositories, subscribers, customers, failures and audit history are visible only to its members, and to operators by an audited, deliberate act.
- **Audit history.** It is the record of who changed access and why. Decision 0007 makes it append-only. Decision 0015 allows exactly one exception.
- **Repository access granted by ShareRepo.** Deleting data must never leave a collaborator that ShareRepo can no longer revoke.
- **Secrets.** These are ShareRepo's own (webhook secrets, `CLAIM_SIGNING_KEY`, `CREDENTIAL_KEYS`) and each tenant's (Paddle API keys and webhook secrets). They must never appear in exports, logs, alert lines or audit details.
- **Personal data.** Logins, emails and claim requests. An export or alert line must not spread them.

## Actors

- **Workspace owner:** can export and delete their own workspace, and retry their own failures.
- **Signed-in user:** can delete only their own account.
- **Operator:** a user whose GitHub account ID is listed in `OPERATOR_GITHUB_IDS`. Sees every workspace's failures on `/ops`, retries or dismisses them, and opens any workspace's Access page read-only.
- **Attacker:** has a ShareRepo account and may own a workspace. Can make a victim's browser send requests, and can guess IDs and URLs.
- **Cloudflare:** delivers queue and dead-letter messages. It is trusted for delivery, not for message contents.

## Threats and mitigations

| # | Threat | Mitigation | Test scenario |
|---|---|---|---|
| O1 | **Operator privilege through configuration.** Someone becomes an operator by changing a database row, renaming a GitHub account to an operator's old login, or exploiting a malformed `OPERATOR_GITHUB_IDS` value. | There is no operator role in the database and no product path that grants one. The list holds immutable numeric GitHub IDs, never logins, and is compared with the signed-in user's linked identity. A value that is not a list of IDs fails the Worker's configuration closed, and an empty or unset value means no operators. Changing the list takes a deploy. | `operator/non-operator-gets-404` |
| O2 | **Discovering `/ops`.** A non-operator learns the page exists, or probes it for data. | `requireOperator` answers 404 to signed-out users and non-operators alike, before any query runs. The route has no client bundle that names it, and no link to it appears outside the operator's own pages. | `operator/non-operator-gets-404` |
| O3 | **Operator queries cross workspaces by mistake.** An operator's retry, dismissal or workspace view acts on the wrong workspace, or a service skips its scoping because the caller is an operator. | Operator services take an explicit `OperatorPrincipal` and an explicit `workspaceId`. Every query still filters by that workspace (decision 0014). Retry and dismiss address a failure by workspace and row ID together. The read-only view uses the owner's scoped services with mutations disabled. | `isolation/cross-workspace-read-denied`, `operator/actions-audited` |
| O4 | **Unaccountable operator action.** An operator retries, dismisses or reads a workspace without a trace. | Every operator action writes an audit event with actor type `operator`, and the actor ID and correlation ID: `job.retried`, `job.dismissed` (with a required reason) and `operator.viewed_workspace`. | `operator/actions-audited` |
| O5 | **An owner reads or retries another workspace's failures.** IDs are guessed or copied from another workspace. | Failure lists and retries are scoped by the owner's workspace (`outbox.workspace_id`, with the open-failures index), never by the row ID alone. Owners cannot dismiss. A system-wide failure (no workspace) is visible only on `/ops`. | `failure/owner-sees-only-own-failures`, `isolation/cross-workspace-mutation-denied` |
| O6 | **Export leaks secrets or personal data.** Credentials, envelopes, token hashes, claim references or emails end up in the downloaded file. | The export is built from an allow-list of fields per table, not from `SELECT *`. Envelopes, token and email hashes, claim references and emails are never selected. A test scans the export for the secret canaries and for email shapes. | `export/contains-no-secrets` |
| O7 | **Cross-tenant or cross-site export.** An attacker downloads another workspace's export, or makes an owner's browser start exports. | The export needs `workspace.manage` in the URL's workspace, through the same scoped lookup as every owner page. Starting it is a POST behind the same-origin check, and the response is an attachment with no CORS headers, so another site cannot read it. It is limited to 5 an hour per workspace and audited as `workspace.exported`. | `isolation/cross-workspace-read-denied`, `deletion/cross-site-request-refused` |
| O8 | **Cross-site or accidental workspace deletion.** A forged request, or a slip, deletes a workspace. | Deletion is a POST behind the same-origin check, needs `workspace.manage`, and is confirmed by typing the workspace slug. It only schedules deletion: the owner can cancel for 30 days, and nothing is purged before then. | `deletion/cross-site-request-refused`, `deletion/workspace-revokes-before-purge` |
| O9 | **Deleting a workspace while access is live.** The purge removes the rows ShareRepo needs to revoke a collaborator, who then keeps the access. | Requesting deletion ends every entitlement (`workspace_deleted`), and reconciliation revokes managed access. The purge waits until no managed grant is active or pending, and the failure pages show why it waits. `deleting` and `purging` refuse writes, checkout and claims. | `deletion/workspace-revokes-before-purge` |
| O10 | **Audit tampering through `purging`.** A bug or attacker sets a workspace to `purging` to unlock deleting its audit history, or deletes account-scoped history. | Database triggers (migration 0009): audit rows can be deleted only while their own workspace is `purging`, and account-scoped rows never. A workspace enters `purging` only from `deleting`, never leaves it, and is never created already being deleted. A CHECK requires a deletion schedule and requester on both statuses. Only the purge job sets `purging`, in the same batch as its first delete, once `delete_after` has passed. UPDATE of audit rows is still rejected everywhere. | `deletion/audit-delete-only-while-purging`, `deletion/purging-is-one-way` |
| O11 | **Purge of the wrong workspace.** A purge job's key, or a missing `WHERE`, deletes another workspace's rows. | The job reads the workspace ID from its key and re-reads the workspace: it must be `deleting` or `purging`, with `delete_after` in the past. Every delete names that workspace ID. The triggers refuse deleting another workspace's audit history, offer versions or unsettled mutations, and foreign keys refuse deleting rows that another workspace's rows still reference. | `deletion/purge-touches-only-its-workspace` |
| O12 | **Deleting someone else's account, or deleting one cross-site.** | Account deletion acts only on the session's own user. It is a POST behind the same-origin check, confirmed by typing the user's GitHub login. It is refused while the user owns a workspace that is not `deleting`. It revokes access before it deletes identity rows, and writes `user.deleted` with counts only. | `deletion/cross-site-request-refused`, `deletion/account-revokes-and-removes-identity` |
| O13 | **Pruning destroys evidence or referenced rows.** Retention deletes a row something still references, or history needed to explain access. | Pruning deletes only by explicit age and state, in bounded batches, and skips every row that something still references (decision 0015). Audit events are never pruned. Unsettled provider mutations can be deleted only by a purge (trigger). Each run writes `data.pruned` with counts per table. | `retention/prune-keeps-referenced-rows` |
| O14 | **Forged or replayed dead-letter messages.** A message on the DLQ makes the consumer run a job, mark the wrong row failed, or fail a row that has already succeeded. | Only Cloudflare can deliver to the DLQ: no Worker has a producer binding for it, and no HTTP path reaches it. The consumer validates the body with the same Zod schema as the main queue. It never runs the job. It marks a row failed only if the row's kind and subject match the message, and only if the row is still unsent and unfailed, so a replay or a stale message changes nothing. | `failure/dead-letter-marks-row-failed` |
| O15 | **The rotation window lasts too long.** While `GITHUB_WEBHOOK_SECRET_PREVIOUS` (or a Paddle `webhook_secret_next`) is set, a leaked old secret still signs valid webhooks. | Both secrets are accepted only during the procedure in the runbook, which ends by removing the old one. Webhooks are hints, so a forged one can only cause a re-read of provider state (AGENTS principle 4). Once the previous secret is unset, old signatures are rejected, and a test proves it. | `rotation/old-and-new-secret-both-accepted` |
| O16 | **Downgrade or key confusion during key rotation.** A reference or envelope is accepted under a key that should be retired, or the wrong key signs new data. | New claim references, email hashes and envelopes always use the keyring's `current` key. Verification tries the other listed keys only while they are listed. Removing a key ends its acceptance, and `rewrap_credentials` moves every envelope off non-current keys first. Envelopes record their key ID, and are bound to their row by authenticated data, so an envelope cannot be moved to another row. | `rotation/old-and-new-secret-both-accepted`, `credential/envelope-bound-to-row` |
| O17 | **A half-finished Paddle webhook rotation.** A failure mid-rotation leaves no valid secret, or accepts unsigned events. | Each step keeps at least one working destination and secret. The second destination and its secret are stored together (a CHECK refuses one without the other), and are promoted only after the old destination is deleted. Disconnecting erases both secrets (CHECK). | `rotation/old-and-new-secret-both-accepted` |
| O18 | **Alert lines leak data.** An alert line carries a login, email, payload or secret into logs and emails. | Alerts go through one helper, `alert(name, ids)`, with a closed vocabulary of names (`ALERT_NAMES`) and fields limited to IDs and codes. Logs pass through redaction. A test runs every job and page with canaries and scans the logs. | `security/no-secrets-in-stored-rows-or-logs`, `audit/no-secrets-in-logs-or-audit` |
| O19 | **Failures nobody hears about.** The cron stops, the sweep lags, or a job dies without a record, so access drifts unnoticed. | Every terminal failure is an outbox row, a `job.failed` audit event and an alert line. The sweep logs a heartbeat each minute and alerts when it lags. A Monitor emails on a missing heartbeat. | `failure/exhausted-job-is-recorded-and-alerted`, `timing/sweep-lag-alerts` |

Open for T6's review:
- A workspace whose GitHub App was uninstalled before its purge waits for ever on managed grants that ShareRepo cannot revoke. An operator must resolve it.
- An account deletion keeps the ID-only `users` row while a connection or offer version still names it. Pruning removes it later.

## Accepted risks

- **Operators see every workspace's failures.** That is the purpose of `/ops`. Failure rows hold IDs and error codes. The affected access is resolved to repository and subscriber names at read time. An operator's reads of a workspace page are audited (O4), but the `/ops` list itself is not audited per view.
- **An operator's GitHub account is a single point of compromise.** Anyone who controls an operator's GitHub account can use `/ops`. GitHub's own account protections (two-factor authentication) are the control. The operator list should stay short.
- **Restoring a purged workspace is an incident procedure.** D1 Time Travel keeps 30 days of history, so the operator can restore a purge only by an in-place restore of the whole database (decision 0015). The runbook treats it as an incident.
- **Monitors is a beta.** If it stops emailing, alerts go unread until the daily `/ops` review (decision 0014).

## Constraints already in the schema (Phase 6 T1)

1. `audit_events_no_delete`, `offer_versions_no_delete` and `provider_mutations_no_delete` allow a delete only while the row's workspace is `purging`. A settled provider mutation may also be pruned. UPDATE triggers are unchanged.
2. `workspaces_purging_one_way`: a workspace enters `purging` only from `deleting`, and never leaves it. `workspaces_created_live`: no workspace is created as `deleting` or `purging`.
3. `workspaces_deletion_scheduled` and `workspaces_deletion_requester`: `delete_after` and the requester are set exactly while the workspace is being deleted.
4. `outbox_dismissed_only_failed` and `outbox_dismissal_complete`: only a failure can be dismissed, and a dismissal names who dismissed it and why.
5. `paddle_connections_next_secret_has_destination`, and `paddle_connections_disconnected_erased` extended to the next secret.
6. `OPERATOR_GITHUB_IDS` parses to numeric IDs or fails closed. Empty or unset means no operators.
