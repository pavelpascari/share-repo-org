# Threat model — operations: operators, export, deletion, dead letters, rotation, alerts

**Status:** Proposed in Phase 6 T1, before the surfaces exist. Decisions [0014](../decisions/0014-failure-handling-and-alerting.md) (failures, dead-letter queue, operators, alerts) and [0015](../decisions/0015-data-lifecycle.md) (retention, export, deletion) define them, and the [Phase 6 plan](../plans/phase-6.md) § Secret rotation defines rotation. T1 built the database side: migration 0009's triggers and CHECKs, and the `OPERATOR_GITHUB_IDS` parser. T3, T4 and T5 implement the rest, each with the scenarios named here. T6 reviews the built surfaces adversarially, then fixes each finding or records it below.

Phase 6 adds the first surfaces that cross workspaces on purpose (operators), move a workspace's data out of ShareRepo (export), or destroy it (pruning, purge, account deletion). Each one can turn a small bug into a cross-tenant leak or an unrecoverable loss.

## Assets

- **Tenant isolation.** A workspace's repositories, subscribers, customers, failures and audit history are visible only to its members, and to operators by an audited, deliberate act.
- **Audit history.** It is the record of who changed access and why. Decision 0007 makes it append-only. Decision 0015 allows exactly one exception.
- **Repository access granted by ShareRepo.** Deleting data must never leave a collaborator that ShareRepo can no longer revoke.
- **Secrets.** These are ShareRepo's own (webhook secrets, `CLAIM_SIGNING_KEY`, `CREDENTIAL_KEYS`) and each tenant's (Paddle API keys and webhook secrets). They must never appear in exports, logs, alert lines or audit details.
- **Personal data.** Logins, emails and claim requests. An export or alert line must not spread them.

## Actors

- **Workspace owner:** can export and delete their own workspace, and retry their own failures.
- **Signed-in user:** can delete only their own account.
- **Operator:** a user whose GitHub account ID is listed in `OPERATOR_GITHUB_IDS`. Sees every workspace's failures on `/ops`, retries or dismisses them, and opens any workspace's Access page read-only.
- **Attacker:** has a ShareRepo account and may own a workspace. Can make a victim's browser send requests, and can guess IDs and URLs.
- **Cloudflare:** delivers queue and dead-letter messages. It is trusted for delivery, not for message contents.

| O9 | **Deleting a workspace while access is live.** The purge removes the rows ShareRepo needs to revoke a collaborator, who then keeps the access. | Requesting deletion ends every entitlement (`workspace_deleted`), and reconciliation revokes managed access. | O10 | **Audit tampering through `purging`.** A bug or attacker sets a workspace to `purging` to unlock deleting its audit history, or deletes account-scoped history. | Database triggers (migration 0009): audit rows can be deleted only while their own workspace is `purging`, and account-scoped rows never. Only the purge job sets `purging`, in the same batch as its first delete, once `delete_after` has passed. | O11 | **Purge of the wrong workspace.** A purge job's key, or a missing `WHERE`, deletes another workspace's rows. | The job reads the workspace ID from its key and re-reads the workspace: it must be `deleting` or `purging`, with `delete_after` in the past. Every delete names that workspace ID. The triggers refuse deleting another workspace's audit history, offer versions or unsettled mutations, and foreign keys refuse deleting rows that another workspace's rows still reference. | `deletion/purge-touches-only-its-workspace` |
| O12 | **Deleting someone else's account, or deleting one cross-site.** | Account deletion acts only on the session's own user. It is a POST behind the same-origin check, confirmed by typing the user's GitHub login. It is refused while the user owns a workspace that is not `deleting`. It revokes access before it deletes identity rows, and writes `user.deleted` with counts only. | `deletion/cross-site-request-refused`, `deletion/account-revokes-and-removes-identity` |
| O13 | **Pruning destroys evidence or referenced rows.** Retention deletes a row something still references, or history needed to explain access. | Pruning deletes only by explicit age and state, in bounded batches, and skips every row that something still references (decision 0015). | O14 | **Forged or replayed dead-letter messages.** A message on the DLQ makes the consumer run a job, mark the wrong row failed, or fail a row that has already succeeded. | Only Cloudflare can deliver to the DLQ: no Worker has a producer binding for it, and no HTTP path reaches it. The consumer validates the body with the same Zod schema as the main queue. It never runs the job. It marks a row failed only if the row's kind and subject match the message, and only if the row is still unsent and unfailed, so a replay or a stale message changes nothing. | `failure/dead-letter-marks-row-failed` |
| O15 | **The rotation window lasts too long.** While `GITHUB_WEBHOOK_SECRET_PREVIOUS` (or a Paddle `webhook_secret_next`) is set, a leaked old secret still signs valid webhooks. | Both secrets are accepted only during the procedure in the runbook, which ends by removing the old one. Webhooks are hints, so a forged one can only cause a re-read of provider state (AGENTS principle 4). Once the previous secret is unset, old signatures are rejected, and a test proves it. | `rotation/old-and-new-secret-both-accepted` |
| O16 | **Downgrade or key confusion during key rotation.** A reference or envelope is accepted under a key that should be retired, or the wrong key signs new data. | New claim references, email hashes and envelopes always use the keyring's `current` key. Verification tries the other listed keys only while they are listed. Removing a key ends its acceptance, and `rewrap_credentials` moves every envelope off non-current keys first. Envelopes record their key ID, and are bound to their row by authenticated data, so an envelope cannot be moved to another row. | `rotation/old-and-new-secret-both-accepted`, `credential/envelope-bound-to-row` |
| O17 | **A half-finished Paddle webhook rotation.** A failure mid-rotation leaves no valid secret, or accepts unsigned events. | Each step keeps at least one working destination and secret. The second destination and its secret are stored together (a CHECK refuses one without the other), and are promoted only after the old destination is deleted. Disconnecting erases both secrets (CHECK). | `rotation/old-and-new-secret-both-accepted` |
| O18 | **Alert lines leak data.** An alert line carries a login, email, payload or secret into logs and emails. | Alerts go through one helper, `alert(name, ids)`, with a closed vocabulary of names (`ALERT_NAMES`) and fields limited to IDs and codes. Logs pass through redaction. A test runs every job and page with canaries and scans the logs. | `security/no-secrets-in-stored-rows-or-logs`, `audit/no-secrets-in-logs-or-audit` |
| O19 | **Failures nobody hears about.** The cron stops, the sweep lags, or a job dies without a record, so access drifts unnoticed. | Every terminal failure is an outbox row, a `job.failed` audit event and an alert line. The sweep logs a heartbeat each minute and alerts when it lags. A Monitor emails on a missing heartbeat. | `failure/exhausted-job-is-recorded-and-alerted`, `timing/sweep-lag-alerts` |

## Accepted risks

The list as it stands after the [Phase 6 risk fixes](#status-after-phase-6-risk-fixes). Risks fixed there are no longer listed here.

- **Operators see every workspace's failures.** That is the purpose of `/ops`. Failure rows hold IDs and error codes. The affected access is resolved to repository and subscriber names at read time. Every read is audited: a workspace page as `operator.viewed_workspace` (O4), the `/ops` lists as `operator.viewed_failures`.
- **The operator's GitHub account itself is a single point of compromise.** Anyone who controls an operator's GitHub account can sign in and use `/ops`, including retry and dismiss after a fresh sign-in. ShareRepo cannot check that the account has two-factor authentication without asking every user for the `read:user` scope ([0014 amendment](../decisions/0014-failure-handling-and-alerting.md#amendment--operator-list-views-are-audited-operator-changes-need-a-fresh-session-phase-6-risk-fixes)). The controls are GitHub's own (each operator keeps 2FA on), a short operator list, the audit trail of every operator read and change, and a two-hour limit on the session that may change failures. Operators can only retry or dismiss; they cannot grant access or read secrets.
- **Restoring a purged workspace is an incident procedure.** D1 Time Travel keeps 30 days of point-in-time history for the whole database, not per workspace, and a purge runs 30 days after the request. Undoing a purge therefore means an in-place restore of the whole database to a point before it, which also rolls back every other workspace's changes since then (decision 0015). No code change can make that per-workspace without a second copy of tenant data, which decision 0015 rules out. The runbook treats it as an incident.
- **Monitors is a beta.** If it stops emailing, alerts go unread until the daily `/ops` review (decision 0014). A second signal exists without new code: `/ops` shows the sweep's last heartbeat and how late the oldest due rows are, so a stalled cron is visible at the review even when no email arrives. Workers Issues emails error groups independently of Monitors.

## Status — rotation threats (Phase 6 T5)

T5 built the rotation surfaces. T6's adversarial review is still to come.

- **O15: mitigated.** `GITHUB_WEBHOOK_SECRET_PREVIOUS` is accepted only while it is set. A Paddle connection's next secret is accepted only while a rotation is in progress, and promotion erases it. Tests show the old secret refused once it is removed, at the GitHub route, at the Paddle route and in the service. The runbook ends the GitHub window within the hour.
- **O16: mitigated.** Claim references are signed, and email and IP hashes computed, only under the current claim key. A retired key verifies references and counts rate limits only while it is listed. `rewrap_credentials` moves every envelope off non-current master keys, and the runbook removes a key only after a run reports none remaining. The next webhook secret has its own AAD purpose (`webhook_secret_next`), so it cannot be swapped with the current secret's envelope.
- **O17: mitigated.** Each step of a Paddle webhook rotation is a guarded write. The second destination is stored before the old one is deleted, and promoted only after that deletion. A failure at each step (create, lost create response, store, delete, lost delete response, promote) leaves at least one working destination and secret, and re-running resumes. Tests cover each case.
- **Residual: an orphaned destination.** When Paddle creates the second destination but its response is lost, ShareRepo never learns its ID. The destination delivers to the connection's URL with a secret ShareRepo does not know, so it is refused with `401`, and it takes one of the seller's 10 slots. Recorded under accepted risks, then fixed by the [Phase 6 risk fixes](#status-after-phase-6-risk-fixes) (R1).
- **Residual: claim emails re-wrapped by the job** are audited by the run's `credentials.rewrapped` counts, not per row. They carry no tenant-visible change: the email is unchanged and erased within the job's run.

## Constraints already in the schema (Phase 6 T1)

1. `audit_events_no_delete`, `offer_versions_no_delete` and `provider_mutations_no_delete` allow a delete only while the row's workspace is `purging`. A settled provider mutation may also be pruned. UPDATE triggers are unchanged.
2. `workspaces_purging_one_way`: a workspace enters `purging` only from `deleting`, and never leaves it. `workspaces_created_live`: no workspace is created as `deleting` or `purging`.
3. `workspaces_deletion_scheduled` and `workspaces_deletion_requester`: `delete_after` and the requester are set exactly while the workspace is being deleted.
4. `outbox_dismissed_only_failed` and `outbox_dismissal_complete`: only a failure can be dismissed, and a dismissal names who dismissed it and why.
5. `paddle_connections_next_secret_has_destination`, and `paddle_connections_disconnected_erased` extended to the next secret.
6. `OPERATOR_GITHUB_IDS` parses to numeric IDs or fails closed. Empty or unset means no operators.

### Considered and fine

- **Operator check.** `OPERATOR_GITHUB_IDS` holds immutable numeric IDs. `external_identities` is unique on (provider, GitHub ID) and on (user, provider), and a relink conflict refuses the sign-in. Deleting an account deletes its identity, so it stops being an operator. `/ops` answers 404 before the same-origin check, any query and any form read.
- **Retry and dismiss scoping.** Both filter by workspace and outbox ID together, with `IS NULL` for system-wide rows. Affected access is resolved only through keys of the row's own workspace. Purge, prune and rewrap rows have no workspace, so no owner reaches them.
- **Dead-letter consumer.** It requires matching kind and subject, and an unsent, unfailed row. There is no producer binding for the DLQ.
- **Export.** It uses a column allow-list (no envelopes, hashes, emails, references or lease tokens). It is POST-only and same-origin, sent `no-store` and `nosniff`, rate-limited and audited. The slug's pattern rules out header injection through the file name.
- **Deletion, cancellation and purge start.** Each is guarded on status in its batch, and `purging` is set with the access checks in the same statement.
- **Rotation.** Start and completion are guarded on stored destination IDs. The next secret has its own AAD purpose, `?v=` is ignored, and rotation needs `workspace.manage`, an active workspace and a same-origin POST.
- **Previous GitHub secret.** It is compared in constant time (`subtle.verify`), an empty value counts as unset, and a malformed header is refused. (A value of only whitespace was accepted; the risk fixes make it fail closed, R4.)
- **Claim keyring.** Keys must be at least 32 bytes in canonical base64, and `current` must be listed. Verification tries every key, and retired rate-limit buckets are counted but never incremented.
- **Alert lines.** The name is written last, and the fields are IDs and classified codes.
- **Audit coverage.** Retry, dismissal, operator view, export, deletion request and cancellation, the purge tombstone, `user.deleted`, `data.pruned`, both rotation stages, `credentials.rewrapped`, `paddle.credentials_rewrapped` and `job.failed` all carry the request's or job's correlation ID. The only unaudited writes are `system_state` and outbox scheduling.

## Status after Phase 6 risk fixes

Phase 6 closed with a pass to fix, rather than accept, the risks above that code can remove. Each fix has a named test; scenario names are in the [testing strategy](../testing-strategy.md#scenario-catalog). ### Residual after the fixes

- **A destination created during a disconnect, by a Worker that then stops before storing it,** stays in Paddle until that workspace connects Paddle again, whose sweep deletes it. A disconnected connection has no key to list with. It delivers to a disconnected connection, which answers `404`, and holds one of the seller's slots.
- **A destination whose creation Paddle reports late** (a lost response where Paddle's list does not show it yet) is deleted by the daily sweep once it is an hour old.

### Product-visible changes

- Operators must have signed in within the last two hours to retry or dismiss on `/ops`; otherwise the page asks them to sign in again with GitHub.
- A link from another site to `/ops` shows a "Continue to operations" page instead of the lists.
- Each Paddle destination ShareRepo creates is described in the seller's Paddle dashboard as `ShareRepo workspace <id> created <time>`, and ShareRepo deletes its own destinations that no longer deliver to a stored connection.
- A Worker refuses to start with a secret that is only whitespace.

### Unverified Paddle assumptions, for the live sandbox check

The [Paddle runbook](../runbooks/paddle-sandbox-setup.md)'s sandbox check should confirm:

- `GET /notification-settings` returns `description` exactly as created, lists inactive settings too, and pages with `meta.pagination` as other lists do (documented, not yet observed);
- the key permission `notification_setting.write` includes listing (documented: write includes read);
- a create whose response is lost shows up in the list at once.
