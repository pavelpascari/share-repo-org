# @sharerepo/db

Drizzle schema, SQL migrations, and workspace-scoped repositories for the shared D1 database. Both Workers bind it as `DB` ([0002](../../docs/decisions/0002-one-wrangler-config-per-worker.md)).

## Schema conventions

- **IDs** are `TEXT`, generated by the caller through the domain `IdGenerator` port. Repositories never call `crypto.randomUUID()`.
- **Timestamps** are `INTEGER` UTC epoch milliseconds (`Instant`), named `*_at`, passed in as `now`. Repositories never call `Date.now()`. Where a row has both, `CHECK (updated_at >= created_at)`.
- **Enumerations** are `TEXT` with a named `CHECK (col IN (...))`. The value lists come from `@sharerepo/domain` constants (for example `WORKSPACE_ROLES`), so the schema and the domain cannot drift silently.
- **Format rules** that SQLite can express are mirrored as named `CHECK` constraints. For example, the slug rule uses `GLOB`, because SQLite has no regular expressions. Tests assert that the database and the domain agree case by case. Where SQLite is weaker (its `trim()` only strips the listed ASCII whitespace), the domain is the stricter gate and the database is the backstop.
- **Constraint names** are `<table>_<rule>`, so violations are recognisable in errors and tests.
- **Tenant tables** ([0004](../../docs/decisions/0004-workspace-scoped-composite-foreign-keys.md)):
  - every workspace-owned table has `workspace_id TEXT NOT NULL REFERENCES workspaces(id)`;
  - it also has `UNIQUE (workspace_id, id)`, or a composite primary key that starts with `workspace_id`;
  - a reference to another tenant table is a composite foreign key, `(workspace_id, x_id) REFERENCES x (workspace_id, id)`, so the database rejects cross-workspace links.

  `test/schema-conformance.test.ts` enforces these rules on the migrated schema. Exemptions must be listed there with a reason.
- **Global tables** (`users`, and later `external_identities`) have no `workspace_id` and use ordinary foreign keys.
- **Deletes** use `ON DELETE RESTRICT`. Removing a workspace or user must be an explicit, audited process that revokes access first. It must never be a silent cascade.
- **Foreign keys** are enforced by D1 by default, and in the local test runtime. A test checks that this stays true.

## Repositories

- Every function takes the Drizzle instance from `createDb(env.DB)` as its first argument.
- Functions that read tenant data take an explicit `workspaceId` and filter on it. `getWorkspaceForMember` only returns a workspace to one of its members.
- D1 has no interactive transactions. A write that must be atomic is a single `db.batch([...])` ([0003](../../docs/decisions/0003-d1-batches-and-transactional-outbox.md)). For example, `createWorkspace` inserts the workspace and its owner membership in one batch. If either insert fails, neither row exists.
- Constraint violations propagate as errors. Outside `batch()`, Drizzle wraps the D1 error, which is available as `error.cause`. The wrapper's message includes the SQL and the bound parameters, so never log it verbatim.
- `ping(db)` runs `SELECT 1` for readiness checks.

## Migrations

Migrations are generated by drizzle-kit and applied by Wrangler. Do not use `drizzle-kit migrate` or `push`.

```sh
pnpm --filter @sharerepo/db db:generate        # after changing src/schema; add --name <change> for a readable file name
pnpm --filter @sharerepo/db db:migrate:local   # local D1 state under apps/web/.wrangler (shared with web dev)
pnpm --filter @sharerepo/db db:migrate:dev     # remote sharerepo-dev
pnpm --filter @sharerepo/db db:migrate:prod    # remote sharerepo-prod (env.production)
```

The verified layout for drizzle-kit 0.31.11 and Wrangler 4.151.1 is:

```text
migrations/
├── 0000_init.sql          # applied by Wrangler and readD1Migrations
└── meta/                  # drizzle-kit snapshots and journal; ignored by Wrangler and Biome, but must be committed
    ├── _journal.json
    └── 0000_snapshot.json
```

- `wrangler d1 migrations apply` and `readD1Migrations(dir)` read only the top-level `*.sql` files, in name order. They record applied names in `d1_migrations`.
- drizzle-kit's `--> statement-breakpoint` markers are SQL comments, so Wrangler accepts them.
- `drizzle-kit generate` must report "No schema changes" on a clean tree. CI checks this. If a generated file is ever edited by hand, the snapshot must still match the schema.
- Tests apply the same files to each test file's empty D1 through `test/setup/apply-migrations.ts`.

### Migrations against a running service

Migrations are applied before the new code deploys ([0002](../../docs/decisions/0002-one-wrangler-config-per-worker.md)), so each one must work with the code that is currently deployed:

- Prefer additive changes: new tables, nullable columns or columns with defaults, and new indexes.
- Split breaking changes into expand, then migrate, then contract, across separate deploys. Never rename or drop a column that deployed code still reads.
- SQLite cannot add a constraint to an existing table. drizzle-kit then generates a table rebuild (create, copy, drop, rename). Review these by hand: check the row counts, check that foreign keys survive, and check that the rebuild is safe while traffic continues.
- Never edit a migration that has been applied anywhere. Add a new one instead.
